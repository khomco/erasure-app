## Intent

**Problem:** A licensing `Feature` (what a customer's licence grants, e.g. `hub_sync`) can be added to the enum with no committed listing recording it, so the website's tier matrix (W3.3), the vendor console and the docs have nothing code-derived to build from (SPEC CAP-3). Separately, the v2 certificate fixture is verified only through in-crate helpers and a seed-derived key; nothing proves the shipped `wipestation verify-cert` command, given the published public key, still accepts a certificate an earlier station signed (CAP-4).

**Approach:** A `wipe-license` integration test reads `Feature`'s variant names from its own serde derive, renders one row per variant into a committed golden `docs/generated/entitlements.txt`, and fails on any difference; `UPDATE_GOLDENS=1` rewrites it (CAP-5). A `wipe-cli` integration test runs the real `wipestation verify-cert` binary on the committed `v2-erased.json` with the committed station public key and requires success; `fixtures_verify.rs` additionally verifies against that committed key literal rather than only the seed.

## Boundaries & Constraints

**Always:** The variant list comes from the derive (a capturing `serde::Deserializer` whose `deserialize_enum` records the `variants` slice), never from a hand list in the test. Each listed name must round-trip through `serde_json` to a `Feature` and back. Each row's summary comes from an exhaustive `match` with no wildcard, so a new variant fails to compile until it has one. Golden: a `# Generated by UPDATE_GOLDENS=1 cargo test -p wipe-license --test feature_listing — do not edit.` header, then one row per variant in declaration order; missing golden fails naming the regen command; CRLF compares equal; failure names the first differing line. The binary test empties the environment (as `help_golden.rs` does) and passes the key as a literal equal to `fixtures/README.md`'s station key.

**Never:** Never edit, regenerate or move `crates/wipe-cert/tests/fixtures/v2-*.json`. No change to `Feature`, its serde names, the CLI, or `verify`. No tier→feature pricing mapping (product decision; L-R8/W3.3 stay open). No new dependencies, crates, xtask, CI config, `sites/` or Astro (D1). Do not touch the other goldens or their tests.

## Autonomous decisions

- **What the "entitlement listing" lists.** The vendor's licence features are what a customer can buy; ROADMAP L-R8 ultimately wants a tier→feature matrix. Options: (a) a feature catalog — wire name and one-line meaning per `Feature`; (b) a tier→feature matrix. Tiers are hub offerings set by a vendor admin and their contents are a pricing decision, so (b) would invent product policy. Chose (a): it is exactly CAP-3's success criterion and the input L-R8's matrix will join against. Summaries restate each variant's existing doc comment; the file is not published (SPEC non-goal), so this is not customer copy.
- **CAP-4 is mostly already in place.** `fixtures_verify.rs` pins the v2 hashes and verifies them; `wipe-cli`'s unit test calls `cmd_verify_cert`. Chose to add only what is missing: the shipped binary on the published key (the surface a third-party verifier uses, W2.5) and a library check against the committed key literal, so a change to seed derivation cannot quietly mask a key mismatch.
- **Portal `FEATURES` mirror.** `apps/portal/src/api/adminOfferings.ts` hand-mirrors the names, and its test pins a hand list. Reading the Rust golden from vitest needs Node types in the app tsconfig — scope growth for a separate package. Deferred (recorded at completion), not built.

## Design Notes

serde's derive passes renamed variant names to `deserialize_enum(name, VARIANTS, visitor)`; a deserializer that stores `VARIANTS` and returns `Err(serde::de::value::Error::custom(..))` yields them with no hand list (forward everything else with `serde::forward_to_deserialize_any!` to an error). Golden shape:

```
# Generated by UPDATE_GOLDENS=1 cargo test -p wipe-license --test feature_listing — do not edit.
enterprise_mode   Customer/Contract/WorkOrder/Asset model (CONTEXT §11 v0.2 #4).
hub_sync          Push certs and config to a hub / control plane.
```
