## Intent

**Problem:** A destroyed drive's certificate is still signed when the Job is *recorded* for destruction: it claims `destroyed` before anyone confirmed anything, and the completion and any concurrence (story 3) sit outside it, on the run in station RAM. A drive that was never erased (every scanned dead drive) gets no certificate at all, so it cannot even join a destruction run. `verify-cert` checks only the signature.

**Approach:** Certificate schema v3 (CAP-4). The Destroy path signs once, on `JobStateChanged` into `Destroyed`, with a `destruction` block holding the run, the honest technique label, the caution, the completion and any concurrence; the attestation stays on the signed Destruction activity. A never-erased drive is certified from its recorded identifiers. `wipe_cert::verify` dispatches on `cert_format_version`: v2 as today (pinned v2 fixture), v3 adds content checks (statements re-render from their fields, concurrence matches the run's requirement, label matches technique). `verify-cert` and the certificate page show who attested, when, how it was verified, and the identity assurance.

## Boundaries & Constraints

**Always:**
- Signing happens only in the cert generator, on `JobStateChanged` into `Erased` or `Destroyed`. Entry into `PendingDestruction` signs nothing. AGENTS.md's certificate-trigger rule says `Erased`/`Destroyed` in the same commit.
- Every new cert is `cert_format_version: 3`, `@context` `…/sanitization-cert-v3`. A v2 certificate must deserialize and re-canonicalize to its signed bytes: every field added or relaxed on a type inside the signed payload is `#[serde(default, skip_serializing_if = "Option::is_none")]` (or equivalent) so v2 JSON round-trips byte-identically. Proven by a committed v2 fixture generated by the **baseline** code before any schema change.
- A Destroyed cert has `destruction` set, and only a Destroyed cert has it. It is built only when the Job's run is `Completed` and has its completion, plus the required concurrence when `required_concurrence` is set, and the Job's latest Destruction activity carries an attestation and the run's `manifest_ref`.
- c779361 in its new form: no Job reaches `Destroyed` uncertifiable. Before `mark_destroyed`, completion/concurrence build every member's `destruction` record against the run as it will be stored; any failure is 409 naming the Jobs, and nothing changes. This replaces story 3's `uncertified` helper; the assembly-time "no certificate" refusal and the desktop's never-erased exclusion are removed.
- `wipe_cert::verify` is the one verifier (CLI and tests call it). v3 refusals are `CertError::Verification` with a reason; an unknown `cert_format_version` is refused by name.
- Statement checks re-render through `wipe_common::{attestation_statement, completion_statement, concurrence_statement}`; never a second copy of the wording.
- Destruction never depends on licence state (ROADMAP §0.2): an unlicensed station still signs, marked `evaluation`.
- Rust and `types.ts` change together; `CONTEXT.md` §5/§10/§12/§14, `README.md`, `docs/ARCHITECTURE.md`, `docs/ROADMAP.md`, `AGENTS.md` change in the same commit.

**Never:**
- No change to the v2 verifier's result for any v2 certificate, and no edit to the committed v2 fixture after generation.
- No co-signature producer: `wipe_cert::co_sign` is removed; `CoSignatureBlock`/`verify_co_signatures` stay for v2.
- No hardware-sanitization claim in cert text, docs or UI (ROADMAP §0.1).
- No SSO/`verified` producer, no persistence of certs or runs, no fix to the deferred abort-strands-a-run item.
- No edits to ADR text.

## I/O & Edge-Case Matrix

|----------|--------------|---------------------------|----------------|
| Erased | erasure completes | v3 cert, no `destruction` key, otherwise as v2 | — |
| Recorded | Job → `pending_destruction` | no certificate (`GET …/certificate` 404) | — |
| Destroyed, erased first, policy none | run completed | one v3 cert: `disposition destroyed`, `destruction.completion` = run's, `concurrence` null, destruction activity `manifest_ref` = run id, `sanitization.method` `destroy/{technique}`, `media_status.damaged` true | — |

| Technique honesty | crush vs shred, classification moderate | crush: `standard_label` "physical damage — not NIST Destroy", `nist_destroy` false, no `sanitization.category`; shred: "NIST SP 800-88 Destroy", category `destroy`, `caution` = SHRED_PULVERIZE_CAUTION | — |

| v3 with co_signatures | any co-signature appended | — | `verify` Err |
| Unknown version | `cert_format_version: 4` (re-signed) | — | `verify` Err "unsupported cert_format_version 4" |
| Uncertifiable member | member whose destruction record cannot be built | nothing changes | 409 naming the Job |

## Autonomous decisions

1. **On a destroyed v3 certificate, `sanitization` describes the destruction, not the last failed erasure.** *About:* the headline "how was this drive sanitized" on a destroyed drive's certificate. *Problem:* v2 put the last erasure attempt's method there (e.g. "NVMe Sanitize — Crypto Erase", category Purge) beside `disposition: destroyed`, and a never-erased drive has no erasure at all. *Options:* (a) keep the erasure summary and require one; (b) the destruction technique, with category `destroy` only for the five NIST techniques and no category otherwise. *Choice:* (b) — ADR-0011 §5 forbids claiming NIST Destroy for crush/punch/degauss/drill, and the failed attempts stay in `activities`. `SanitizationBlock::category` becomes optional (absent only for non-NIST destruction).
2. **`device` and `capabilities_snapshot` become optional, omitted for a drive never erased.** Synthesizing a device would claim it was read from the drive; the attestation's identifiers and their `source` are the honest record (ADR-0011 §2).
3. **The attestation is not copied into the `destruction` block.** It is signed once on the Destruction activity the block names (`destruction_event_id`); verify checks the link (same reasoning as story 1 decision 3).
4. **`verify` refuses inconsistent v3 content and any v3 co-signature.** A signed but self-contradicting record (statement not matching its fields, a reviewer stored as witness) must not pass as verified; v3 carries concurrence inside the signed bytes, so a co-signature on v3 can only have been appended after the fact. The signature-only v2 path is unchanged.
5. **The run link is now signed.** The generator's strip of `manifest_ref` existed because signing preceded assembly; it now follows completion, so the link is final and belongs in the record.
6. **Certificates stay asynchronous** (as for `Erased`): the completion response may precede the certificate by milliseconds; the preflight guarantees it can be built. Clients poll as the certificate page already does.
7. **Destroyed media status is `operational: false, damaged: true`**; a never-started Job's `started_at` is its `created_at`. The licence quota still counts a non-evaluation destroyed certificate, as it did at pending destruction.
